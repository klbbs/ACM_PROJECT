# AI 复盘与远程提交跟踪：原故障排查记录

本次保持版本 0.21.5，不打标签、不制作发布包。用户明确要求到服务器定位这两项线上故障，操作范围仅限对应日志、原任务、原提交及必要的 web 修复。

## 原问题与证据

- 服务器 10 月 27 日 12:28～12:29 的四次 `submission_review` 均失败。原始 Codex 本地日志确认上游 HTTP 400、`invalid_json_schema`、`required` 缺少 `minimal_change_idea`，未观察到这四次失败是额度、认证或限流导致。只提取固定分类与布尔证据，未输出上游正文、源码或凭据。
- `SubmissionReview` 的可空可选字段原样传给严格结构化输出，但未列入全部必填字段。官方文档要求所有输出属性列为 required，以 null 表达可空值：[结构化输出说明](https://developers.openai.com/api/docs/guides/structured-outputs)。
- 官方通道丢弃 `turn.error.codexErrorInfo`，将所有失败统一提示成“检查额度、模型权限或重试”，业务日志也只有 `ai_task_failed`，掩盖了根因。
- 今日原远程任务没有提交号，状态停在 uncertain/receipt_unavailable；找回回执没有传入已经绑定的 CF API 凭据，仍调用已受限的网页源码入口。前端 uncertain 不触发自动恢复。
- 原题的既有官方源码与本站当时发送代码的实际 SHA-256 相同，账号、题号、时间窗口一致。接入 API 后又发现编辑器模式 cpp17、实际官方 C++23、既有源码模式 cpp20 的内部标签冲突，因而被误拒绝；并非题号或源码不一致。

## 实现

- 共享严格输出适配：复制 schema，在对象与嵌套定义中要求全部属性，保留 nullable、引用和原约束，去除默认值元数据；本地 Pydantic 校验保持原语义。官方账号、Responses、Chat 及原生 schema API 共用修复；显式动态字典不被静默丢弃。
- 官方失败按固定枚举区分 schema、认证、额度、限流、上下文、模型、网络与未知原因，只保留有界数字 HTTP 状态。重试通知等待真正终态，拒绝旧回合与无归属内容，不把失败的部分输出作为报告。修复仅有 model 字段的模型目录条目导致的异常。
- 未知回执找回使用已绑定 CF API，保留本人、题号、时间窗口、唯一提交和实际源码哈希核验；缺 API 与其他失败原因明确展示，不发送代码、不猜最新提交。
- 根据官方编译器规范保存工作台语言；仅允许 C++17/C++20 编辑器标签在同语言族内校正，拒绝跨语言、未知官方语言、不同代码及损坏哈希。仅当已有记录标签确实校正时失效该条旧复盘，其他报告保留，原发送任务的代码与标签保持不变。
- 前端对未知回执按间隔最多恢复三次，遵守限流和认证停止条件；末次请求后继续有界观察后台结果，不重发代码。暂停查询与“官方判题中”分别显示，已取得回执的异常不会误改为提交失败。
- 真正排队重试时清除旧失败原因，保留限流与已有任务守卫；手动重试重新开启有界结果观察，但不重置自动查询次数，避免后台已成功而页面停在旧状态，也避免无限自动请求。
